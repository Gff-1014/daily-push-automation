# 四级听力音频播放问题 · 调整思路整理（v1）

> 现状：对照页音频在用户环境始终无法播放；期间已尝试 5 种页面内播放方案均失败。
> 本文件整理已验证事实、根因假设、可选方案与建议路径，作为下一步决策依据。

---

## 一、问题现象

- 邮件听力板块指向 COS「听力对照页」，页面能打开，但音频无法播放；
- 早期版本（邮件内三个 mp3 直链）曾出现「点链接进入播放器、离开后不继续、无法边听边看原文」的反馈，
  说明**直链在用户环境可以唤起系统/浏览器原生播放器并播放**；
- 此后所有页面内嵌播放方案均不可播。

## 二、已尝试方案与结果

| 版本 | 方案 | 用户环境结果 | 本机验证结果 |
| --- | --- | --- | --- |
| 1 | 邮件三个 mp3 直链 | 可打开原生播放器（早期反馈），但无法边听边看 | 文件 200 / 可下载 |
| 2 | COS 对照页 + `<audio src>` 直写标签 | 不可播 | 无头 Edge：readyState=4，可播 |
| 3 | `<audio>` + 大按钮（手势内设源播放） | 不可播 | — |
| 4 | 手势内动态创建 `<video>`（playsinline / x5 属性） | 不可播 | 无头 Edge：readyState=4，播放中 |
| 5 | Web Audio API 同源 fetch 解码播放 | 不可播 | JS 语法通过；本地文件探针正常 |

## 三、已验证事实

1. **音频文件本身有效**：ffmpeg 可解析（时长 31 秒），COS 返回 200 / 206（Range 支持）、`audio/mpeg`；
2. **桌面真实浏览器可播**：无头 Edge 分别验证了 audio、video、动态创建三种方式均 readyState=4；
3. **页面与文件均可公开访问**：页面 200、三份 mp3 均 200；
4. **用户环境特征**：页面内所有播放方式失败，但直链可唤起原生播放器（早期反馈）；
5. **缺少关键信息**：用户设备型号 / 系统 / 打开方式 / 点击后的具体现象，尚未提供。

## 四、根因假设（按可能性排序）

1. **用户所用 App 内置 webview 禁用了页面内媒体播放**：媒体元素（audio/video）与 Web Audio 均被限制，
   只有系统级原生播放器可用——与「直链可播」现象吻合；
2. **页面 JS 未执行**：若 webview 禁 JS，动态创建类方案（video、Web Audio）全灭；
   但静态 `<audio src>` 理论上仍可手动播放，若该版也失败，则更支持「媒体被禁」假设；
3. **用户网络/设备对该 COS 域名媒体请求受限**：HTML 能加载但媒体字节拉不动；
   若直链同网络下也无法播放则支持此假设（与早期反馈矛盾，可能性较低）；
4. **其他**：邮件客户端改写链接、缓存了旧页面、时区/日期差异等（低概率）。

## 五、可选方案对比

| 方案 | 可行性 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A. 邮件原文对照 + 系统播放器直链 | 高 | 100% 可播，实现简单 | 播放时离开邮件/页面，无法同屏对照（原始痛点仍在） |
| B. mp3 附件随邮件发送 | 高 | 任何播放器可播、可下载、可离线 | 用户此前否决；邮件变大；无倍速控制 |
| C. 第三方成熟播放页（如 tingroom 原页） | 中 | 对方播放器经过大量移动端适配 | 无法带我们的原文/翻译/倍速排版；可能有广告 |
| D. 自定义域名 / CDN 托管音频 | 中 | 可能绕过域名级限制 | 需要域名+备案；不解决 webview 禁媒体的问题 |
| E. 诊断页（自动检测各播放方式） | 高（先做） | 拿到根因证据，避免盲改 | 需要用户配合查看/反馈页面结果 |
| F. 保留页面方案 + 常驻「用系统播放器打开」按钮 | 中 | 页面先看原文，点按钮用原生播放器听 | 仍无法同屏对照 |

## 六、建议路径

### 第一步：先取证，不再盲改

制作一个「听力诊断对照页」并上传 COS（内容仍是当日听力），页面自动检测并显示：

- 页面是否正常加载、JS 是否执行；
- fetch 音频字节是否可达（同源）；
- `<audio>` / `<video>` / Web Audio 三种方式各自的加载状态与时长；
- 直链是否可打开。

用户打开诊断页后，把页面顶部显示的结果（截图或文字）发回，即可锁定根因。

### 第二步：按诊断结果分流

| 诊断结果 | 对应方案 |
| --- | --- |
| fetch 不可达 / 媒体字节拉不动 | 换托管（CDN / 自定义域名） |
| JS 未执行 | 页面方案不可行 → 转方案 A / B |
| 仅 Web Audio 不可用，video 可用 | 回到 video 方案微调 |
| 全部页面内方式不可用，直链可播 | 采用方案 A（邮件内原文 + 系统播放器直链），页面方案降级为可选 |
| 全部不可用且直链不可播 | 与早期反馈矛盾，需重新核对网络/设备 |

### 第三步：定稿实现

- 依据诊断结论实现最终方案；
- 涉及邮件模板时再发测试邮件；在定稿前不再反复改播放器代码。

## 七、需要用户提供的信息（关键）

1. 设备型号 + 系统（iPhone 还是安卓，什么牌子/型号）；
2. 在哪里打开：QQ 邮箱 App 内直接点、网页版邮箱、还是复制链接到浏览器；
3. 点「开始播放」后的具体现象：按钮没反应 / 一直「加载中」/ 页面提示错误 / 有声音但很小等；
4. 页面出现「用系统播放器打开」时，点它能否播放；
5. 早期直链版本现在能否播放（验证网络是否变化）。

---

> 结论：在拿到用户环境证据前，继续调整页面播放器属于盲改。建议先发诊断页取证，
> 再按分流表确定最终方案。
